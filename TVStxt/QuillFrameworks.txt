# Quill 写作框架库 (7 套结构)

源自 wewrite/references/frameworks.md, 精华压缩版。每套框架是文章骨架 (告诉你"每段写什么"), 不是文章本身。**根据选题特征和 content_style 选 1 套用, 不要混用**。

## 7 套框架速查

| 框架 | 适合选题 | 最佳 content_style |
|------|---------|-------------------|
| A 痛点型 | 解决问题、提供方案 | 干货 |
| B 故事型 | 人物、事件、趋势 | 故事 / 情绪 |
| C 清单型 | 盘点、推荐、方法论 | 干货 / 测评 |
| D 对比型 | 选择、决策、A vs B | 测评 / 干货 |
| E 热点解读型 | 新闻、事件、行业动态深度解读 | 热点 |
| F 纯观点型 | 表达立场、反驳主流、价值判断 | 情绪 / 热点 |
| G 复盘经验型 | 个人实践、项目复盘、阶段回顾 | 干货 / 故事 |
| H 技术实战型 | 技术教程、工具实战、架构解析、源码走读 | 技术 |

content_style → 推荐顺序:
- 干货 → 痛点、清单、复盘
- 故事 → 故事、热点解读、复盘
- 情绪 → 故事、痛点、纯观点
- 热点 → 热点解读、对比、纯观点
- 测评 → 对比、清单
- 技术 → 技术实战 (专用框架, 不映射到其他)

---

## 框架 A: 痛点型

**适合**: 解决问题、提供方案的选题。干货型首选。

1. **开头 (痛点共鸣)** — 直接描述目标读者正在经历的痛点场景。用 "你是不是也..." 切入。制造紧迫感: 不解决会怎样。
2. **痛点放大 (H2)** — 用数据/案例说明问题有多普遍 + 分析为什么大多数人的做法是错的。金句落点: 一句话总结错误认知。
3. **解决方案 (H2)** — 核心方法/工具/思路 ≤ 3 个要点, 每个配具体案例或操作步骤。金句: 一句话总结方法论。
4. **实操验证 (H2, 可选)** — 用一个完整案例走一遍, 或用前后对比展示效果。
5. **结尾 (行动引导)** — 一句话总结核心 + CTA: 引导留言分享自己的痛点或转发给同样的朋友。

---

## 框架 B: 故事型

**适合**: 人物、事件、趋势类。故事型/情绪型首选。

1. **开头 (悬念钩子)** — 抛出反直觉的结果或意外场景。"谁也没想到..." / "所有人都以为...结果..."。**不要剧透结论**。
2. **背景铺垫 (H2)** — 时间、人物、起因, ≤ 200 字快速过渡。金句: 定义故事的核心矛盾。
3. **转折与高潮 (H2)** — 关键转折点, 用细节还原 (对话/数字/画面)。**全文最花笔墨的地方**。
4. **深度解读 (H2)** — 从故事上升到规律/趋势/洞察。这个故事对读者意味着什么。金句: 你看到的本质。
5. **结尾 (情绪共振)** — 回扣开头悬念 + CTA: "你身边有没有类似故事"。

---

## 框架 C: 清单型

**适合**: 盘点、推荐、方法论。干货/测评首选。

1. **开头 (价值承诺)** — 直接告诉读者 "看完能得到什么"。用数字锚定: "5 个方法" / "3 个工具" / "7 个坑"。简短说为什么你有资格推荐。
2. **清单项 1-N (每项一个 H2)** — 每项: 名称 → 一句话说明 → 具体案例/场景 → 适用人群。**项与项长度不一**, 避免机械感。每 2-3 项穿插金句或个人吐槽打破节奏。**建议 5-7 项, ≤ 10**。
3. **结尾 (总结 + 彩蛋)** — 一张表格或一句话总结全部 + 加一个 "隐藏推荐" / "个人最爱" 彩蛋。CTA: "你还知道哪些"。

---

## 框架 D: 对比型

**适合**: 选择、决策、A vs B。测评/干货首选。

1. **开头 (选择困境)** — 描述读者面临的 "选 A 还是 B" 困境, 说明为什么这个选择重要/容易选错。
2. **A 方案深度分析 (H2)** — 优势 2-3 点 (每点配案例) + 劣势 1-2 点 (诚实说) + 最适合什么场景。金句: 定义 A 的核心价值。
3. **B 方案深度分析 (H2)** — 同样结构, 与 A 形成对照。金句: 定义 B 的核心价值。
4. **对比总结 (H2)** — 表格对比 3-5 个关键维度。明确给出 "X 情况选 A, Y 情况选 B" 的结论。**不要和稀泥说 "各有优劣"**。
5. **结尾 (个人选择)** — "如果是我, 我选 X" + 为什么。CTA: 投票或留言 "你选哪个"。

---

## 框架 E: 热点解读型

**适合**: 新闻、事件、行业动态深度解读。热点型首选。

1. **开头 (事件速览)** — 2-3 句话说清楚发生了什么 (5W1H 精简版), 用自己的话, 不复制新闻原文。判断句结尾: "这件事比表面看起来复杂得多"。
2. **表面信息 (H2)** — 媒体怎么报道、网友怎么评论, 简要梳理主流观点。金句: 指出主流盲区。
3. **深层分析 (H2)** — 你看到了什么别人没看到的, 背后的利益链/技术逻辑/行业趋势。用 1-2 个类比或历史事件对照。金句: 你的核心判断。
4. **影响预判 (H2)** — 短期: 接下来会怎样。长期: 对行业/普通人意味着什么。说清楚不确定性: "如果 X 发生, 则 Y; 如果不发生, 则 Z"。
5. **结尾 (读者行动建议)** — 普通读者应该怎么应对/关注什么。CTA: 关注后续或留言看法。

---

## 框架 F: 纯观点型

**适合**: 表达立场、反驳主流、输出价值判断。情绪/热点首选。**与热点解读区别**: 不需要从新闻事件出发, 直接从论点开刀。

1. **开头 (亮刀子)** — 第一段就把核心观点甩出来, **不铺垫**。观点够尖锐, 让读者要么点头要么皱眉。"我越来越觉得 X 是一个巨大的谎言" / "所有人都在说 X, 但没人提 Y"。
2. **为什么我这么想 (H2)** — 触发观点的**具体经历或观察** (不是抽象推理), 1-2 个亲眼见过/亲身经历的案例。金句: 把观察提炼为一句判断。
3. **主流观点哪里错了 (H2)** — 列出主流说法, 逐条反驳。**不要稻草人** — 引用真实对立观点, 给对方最强版本, 再说明为什么仍不同意。承认对方有道理的部分。金句: 分歧的本质。
4. **如果我是对的, 意味着什么 (H2)** — 推演观点的后果 (对读者/行业/普通人), 给一个可验证的预测或判断标准 ("如果半年后 X 发生, 说明我说对了")。
5. **结尾 (留余地但不软)** — **不要总结**, 不要 "综上所述"。承认自己可能错, 但说清楚在什么条件下你会改变看法。CTA: "你同意吗? 评论区见"。

---

## 框架 G: 复盘/经验型

**适合**: 个人实践总结、项目复盘、阶段性回顾。干货/故事首选。**与故事型区别**: 主角是 "我", 重点是可迁移经验, 不是戏剧性。

1. **开头 (结果先行)** — 先说结果/数据: 做了什么、多久、成果如何。**不要谦虚也不要吹**, 直接上数字。"做了 3 个月, 踩了 X 个坑, 最后 Y 还行, Z 彻底失败"。
2. **背景和动机 (H2)** — 为什么做、起点状态, ≤ 150 字快速过渡。金句: 一句话说清当时认知 ("那时我以为 X, 现在觉得自己太天真")。
3. **做对了什么 (H2)** — 2-3 个关键决策, 每个配具体数据/结果。**说清楚 "为什么当时选了这个方向"** — 决策过程比结果更值钱。金句: 提炼为可迁移原则。
4. **做错了什么 (H2)** — **全文最值钱的部分**。每个错误: 当时怎么想 → 实际发生了什么 → 现在回头看应该怎么做。**不要轻描淡写** — 具体到金额、时间、情绪代价。金句: 这个坑的本质。
5. **结尾 (如果重来)** — "如果重新来过, 我会..." 给 2-3 条具体建议。**不要泛泛** — 具体到 "第一周先做 X, 不要碰 Y"。CTA: 引导读者分享复盘或提问。

---

## 框架选择决策树

```
是个人经历/项目复盘吗? → G 复盘型
是技术教程/工具实战/架构解析吗? → H 技术实战型
有明确的"选A还是B"吗? → D 对比型
是新闻/热点事件的解读吗? → E 热点解读型
是表达尖锐立场反驳主流吗? → F 纯观点型
是讲一个人/事件/趋势的故事吗? → B 故事型
是盘点/推荐/方法论清单吗? → C 清单型
其他 (解决问题, 提供方案) → A 痛点型 (默认)
```

## 框架 H: 技术实战型

**适合**: 技术教程、工具实战、架构解析、源码走读、AI/编程领域深度教学。与痛点型/清单型的本质区别——**代码和踩坑记录是核心价值，文字只是胶水**。

1. **开头 (共鸣困境)** — 一个开发者真实会遇到的具体困境，不要行业背景铺垫。用具体时刻 + 具体痛点切入，让读者产生"对，我也遇到过"的反应。禁止: "在当今 AI 时代..." "随着技术发展..." 等套话。示例: "凌晨两点，你第 N 次看到用户反馈：'我问的是营收增速趋势，它给我贴了三页财报原文。'你的 RAG 系统跑得稳稳当当——但它就是不思考。"

2. **问题拆解 (H2)** — 把大问题拆成 2-3 个具体技术子问题。一句话说清每个子问题的本质。示例: "本质上要解决三件事: ① 怎么让模型知道该查哪个库? ② 查一次不够时怎么让它自己再查? ③ 工具多了怎么管理?"

3. **方案演进 (H2 × N，全文核心，占 60%+ 篇幅)** — 每个 H2 一个技术方案，按"简单→复杂→生产级"递进。每节必须包含 **四个不可删减元素**:
   - **为什么选这个方案** (一个自然段，说清楚选型理由)
   - **完整可运行代码** (不是伪代码，不是删减版，关键代码 ≥ 20 行必须完整保留，标注语言)
   - **跑了会看到什么** (关键输出/效果/性能数据，用具体数字)
   - **这个方案的局限** (诚实说，不要回避——"文档 ≤ 50 页时没问题，超过 200 页延迟会涨到 3 秒以上")

4. **进阶扩展 (H2)** — 从单点到体系。"单文件跑通了，但如果要做生产级系统..." 引入更高阶的架构或工具组合，同样带完整代码。

5. **收尾 (一条洞察，不做总结)** — 给出一个可引用、有观点的技术判断，呼应开头的问题。不做"综上所述"，不给"未来展望"。示例: "Router 解决了去哪找，Tool Calling 解决了怎么找，ObjectIndex 解决了工具多了怎么管。三者叠加，构建的不是一个更聪明的检索器，而是一个知道自己不知道什么、并且知道怎么去知道的系统。如果你的 RAG 还停留在'查到了就答，查不到就编'——那不是够用，那是还没开始用。"

**⚠️ 技术实战型特别约束 (区别于其他框架)**:
- **字数放开**: 2500-5000 字 (含代码块)，代码块不计入字数压缩目标
- **不可删减**: import/依赖声明、代码块、对比表格、版本号、API 名、参数说明、错误信息/踩坑记录——一律完整保留
- **每 H2 ≥ 1 个代码块**，代码前一行说明"这段代码做了什么"，代码后跟输出/效果
- **删减优先级** (必须压缩时): 先砍形容词 → 再合并重复论述 → 最后才动代码 (且仅限修剪注释)
- **禁止行为**: 把代码块替换为文字描述、把对比表合并成自然段、省略 import 和依赖声明

## 通用规则 (所有框架)

- **H1 标题 20-28 字** — 微信标题字段, converter 自动提取
- **金句落点** — 每个标注"金句落点"的位置放一句精炼总结 (≤20 字, 有观点, 能截图发朋友圈)
- **写作时不要插入配图占位符** — 配图由 ZImageGen/ComfyUIGen 在终稿后生成
- **不要混用框架** — 选一套从头到尾用
