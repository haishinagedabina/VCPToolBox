# 小说黑板台账规范

## Overview

长篇创作的一致性不靠模型记性，靠沉盘的结构化台账。每个 Agent 每次被唤起都是全新会话，只读它需要的那 1–2 个文件。进程死了，读台账就能续。

本技能定义黑板上每个文件的字段格式、谁能写、怎么写。**违反单写入者原则或用错写入命令会导致台账静默损坏**，这是本系统最高危的两类故障，所以放在最前面。

## Quick Reference

一律用 `tool_name:「始」ServerFileOperator「末」`，**严禁 `FileOperator`**——后者会被路由到桌面分布式节点，既无权访问 `E:\VCPChat\VCPToolBox`，又会命中人工审核卡死。不要为了"换个方式试试"就改用 `FileOperator`。

| 我要做什么 | command | 必需参数名 |
|---|---|---|
| 首次创建台账文件（**必须先 `FileInfo` 探测确认不存在**） | `WriteFile` | `filePath` + `content` |
| 刷新快照型台账（整份覆盖） | `EditFile` | `filePath` + `content` |
| **追加累积型台账**（`timeline.md`、`log/debt.md`） | `AppendFile` | `filePath` + `content` |
| 局部修改章节正文 | `ApplyDiff` | `filePath` + `searchString` + `replaceString` |
| 读台账 | `ReadFile` | `filePath` |
| 落盘后验证 | `FileInfo` | `filePath` |
| 列目录 / 建目录 | `ListDirectory` / `CreateDirectory` | **`directoryPath`** |

**区分快照型与累积型台账，这决定用哪个命令。**

| 型 | 文件 | 命令 | 原因 |
|---|---|---|---|
| 快照 | `status_card.md`、`cognition.md`、`progress.md`、`run.md` | `EditFile` | 只反映当前状态，旧值不保留，整份覆盖是对的 |
| 累积 | `timeline.md`、`log/debt.md` | **`AppendFile`** | 只追加新行、从不改写既有行。用 `EditFile` 意味着每章要把整张表原样重打一遍，到 50–100 章时会超过 `maxOutputTokens` 被**静默截断**，一次截断就永久丢历史 |
| 混合 | `hooks.md` | `EditFile` + 归档 | 需要改既有行（更新推进章、状态），但必须把 `已回收`/`已废弃` 的行迁出到 `hooks_closed.md`（用 `AppendFile`），保持活跃表不膨胀 |

累积型台账被静默截断是本系统最隐蔽的故障：它不报错，而且正好砸在"一致性全靠台账"这个立足点上。

⚠️ **`ListDirectory` 与 `CreateDirectory` 用 `directoryPath`，不是 `filePath`。** 传错会报 `The "paths[0]" argument must be of type string. Received undefined`。这是本系统最高频的调用错误。

### ⛔ 写"新建"文件的顺序：先 `EditFile`，报错才 `WriteFile`

`WriteFile` 撞到同名文件时**不覆盖、不报错**，而是自动改名成 `ch003(1).md`。磁盘上于是出现多份内容不同、名字相近的同章产物，下游各读一份，一致性从这里开始崩，**全程没有任何错误提示**。这是本系统唯一"静默且不可逆"的故障。

**所以顺序固定为：**

1. 直接 `EditFile`。成功即说明文件本来存在、已被覆盖——**重复写入时这正是希望发生的事**。
2. 只有 `EditFile` 报"文件不存在"，才改用 `WriteFile` 新建。报错是响亮的，不会漏看。

⛔ **报错之后是"换命令"，不是"再试一次"。** 首次写某章产物时 `EditFile` **必然报错**，这是预期结果而非故障；下一步必须把同样的 `filePath` 与 `content` 改用 `WriteFile` 发出。**实测事故**：对 `summaries/ch005.md` 连发 3 次 `EditFile` 全部报错、一次都没回落到 `WriteFile`，该章摘要**根本没被创建**，回执却说已验证通过。

⛔ **不要用"先 `FileInfo` 探测再判断该用哪个"代替这条。** 那个写法实测失败过：探测确实调用了，但第三遍写入时模型仍然选了 `WriteFile`，撞名生成 `ch004(1).md`。**判断分支不可靠，所以要把安全动作设成默认动作**，而不是把它放在一个需要判断才能到达的分支里。

### ⛔ `AppendFile` 不会替你补换行 —— content 必须以换行开头

`AppendFile` 底层是 `fs.appendFile(filePath, content)` 裸拼接（`Plugin/FileOperator/FileOperator.js:696`），**不插任何分隔符**。如果上一次写入没以换行结尾，而这次的 content 又不以换行开头，新行就会被**粘在上一行末尾**，表格结构当场破掉：

```text
| 进宗三年 · 第1天夜间 | ...将剑藏于枕下 | 许灵匀 | 001 || 进宗三年 · 第1天深夜 | 赵执事带刘疤子夜搜... | 002 |
```

这一行现在既不是合法表格行，也再也无法靠"按行读"解析回来。**实测发生过，`timeline.md` 被粘出 3 处。**

**所以：`AppendFile` 的 `content` 一律以 `\n` 开头。** 不要依赖"上一次应该是以换行结尾的"——你无法验证上一次是谁写的、怎么结尾的，而这个假设一旦错一次就永久损坏。以换行开头是幂等的：多一个空行无害，少一个换行则致命。

```text
content:「始」
| 进宗三年 · 第2天清晨 | 事件描述 | 许灵匀 | 003 |「末」
```

同一条纪律适用于所有 `AppendFile` 目标：`timeline.md`、`hooks_closed.md`、`log/debt.md`。**只在一处照做是不够的**——实测中 `timeline.md` 补了前导换行、`hooks_closed.md` 漏了，结果分隔行与第一条数据行粘成 `|---|---|---|---|---|| H003 | ...`，归档表整张失效。**每次 `AppendFile` 都独立检查 content 首字符。**

**同一工具连续失败 2 次即停手**，不要第 3 次重复相同调用。在回执里如实汇报"什么命令、什么参数、什么报错"，让总编裁量。同样的参数只会同样地失败。

遇到 `ENOENT` 时的正确排查顺序：先 `ListDirectory`（用 `directoryPath`）列出目录拿到**真实文件名**，再用真实文件名重发。**文件名从不靠记忆猜**——章号、日期都必须从任务 prompt 或上游回执里原样复制。

## 一、两条铁律

### 1.1 `EditFile` vs `WriteFile`

**`WriteFile` 遇到同名文件不会覆盖，而是自动改名。** 写 `status_card.md` 时若该文件已存在，会被写成 `status_card(1).md`，下一次变成 `status_card(2).md`。台账会分裂成一堆互不相干的版本，一致性彻底失效，而且**不会报错**——这是静默故障，最难发现。

所以：

- 刷新已存在的台账 → **`EditFile`**（文件不存在时会报错，这正是我们要的保护）
- 只有首次创建（`FileInfo` 确认文件不存在）→ `WriteFile`

刷完后用 `FileInfo` 验证路径与预期完全一致，确认没有出现带序号的文件名。

### 1.2 单写入者原则

台账刷新是整份覆盖，所以**每个文件只能有一个写入者**，否则两个 Agent 会互相清掉对方写的字段。

| 文件 | 唯一写入者 |
|---|---|
| `book.md`、`compass.md`、`outline.md`、`characters.md`、`world.md`、`style.md` | 架构师 Atlas |
| `arcs/arcNN.md` | 架构师 Atlas |
| `state/` 下 6 份台账的**首次创建**（空模板） | 架构师 Atlas（建基那一棒，见第七节） |
| `plans/chNNN.plan.md` | 执笔 Inkwell |
| `chapters/chNNN.md` | 执笔 Inkwell 首写；修订 Chisel 精修时覆盖 |
| `reviews/chNNN.verdict.md` | 审稿 Umpire |
| `state/status_card.md`、`state/hooks.md`、`state/hooks_closed.md`、`state/timeline.md`、`state/cognition.md`、`state/progress.md` 的**后续刷新** | 记账 Ledger |
| `summaries/chNNN.md` | 记账 Ledger |
| `state/run.md`、`log/debt.md` | 总编 Muse |

「首次创建」与「后续刷新」分属不同 Agent 不违反单写入者原则——它们在时间上严格不重叠，且创建的是空模板不含任何内容判断。这个分工是为了解开冷启动死结（第七节）。

**不是你的文件，一个字都不要写。** 需要别人改，就在回执里说明，由总编派人。

## 二、黑板目录结构

```
file/novel/<book-id>/
├── book.md                  # 元信息：书名 / 题材 / 主角 / 目标章数 / 目标篇幅
├── compass.md               # 指南针：终局方向 + 活跃长线 + 规模估计
├── outline.md               # 分层大纲：当前卷详细章节 + 后续卷仅 goal + 预估章数
├── characters.md            # 角色档案
├── world.md                 # 世界规则与设定
├── style.md                 # 本书文风契约 + 禁忌清单 + 题材禁用风格黑名单
├── state/
│   ├── status_card.md       # 当前状态卡（快照，EditFile）
│   ├── hooks.md             # 伏笔池 · 活跃（EditFile）
│   ├── hooks_closed.md      # 伏笔池 · 已回收/已废弃归档（AppendFile）
│   ├── timeline.md          # 时间线（累积，AppendFile）
│   ├── cognition.md         # 角色认知（快照，EditFile）
│   ├── progress.md          # 内容事实（Ledger 写，EditFile）
│   └── run.md               # 编排运行态（Muse 写，EditFile）
├── plans/chNNN.plan.md      # 章节节拍表
├── chapters/chNNN.md        # 章节终稿
├── reviews/chNNN.verdict.md # 评审判决
├── summaries/chNNN.md       # 章摘要
├── arcs/arcNN.md            # 弧摘要
└── log/debt.md              # 带病上线记录
```

约定：`chNNN` 三位零填充（`ch001`、`ch012`、`ch120`）。`arcNN` 两位（`arc01`）。`book-id` 用 kebab-case ASCII，不要用中文，避免路径编码问题。路径统一用 Windows 绝对路径。

## 三、台账字段规范

### 3.1 `state/status_card.md` —— 当前状态卡

回答的问题：**"现在是什么局面？"** 每章由记账整份覆盖。

```markdown
# 状态卡 · 截至第 NNN 章

## 进度锚点
- 最新完成章: 第 NNN 章《标题》
- 当前卷 / 弧: 第 N 卷 · 第 N 弧（弧型: 成长突破）
- 故事内时间: <故事内的当前时间点>
- 主角当前位置: <地点>

## 主角状态
- 实力 / 境界: <当前> （上章为 <前值>）
- 身份 / 处境: <一句话>
- 持有关键物: <清单>
- 当前目标: <短期目标>
- 当前主要障碍: <一句话>

## 关键配角在场状态
| 角色 | 当前处境 | 与主角关系 | 最近出场章 |
|---|---|---|---|

## 势力 / 组织态势
- <势力名>: <当前态势>
```

写作要求：

- 「上章为 <前值>」这一栏取自**上一版状态卡**的对应字段，不要从正文里重新推断。这是变化追踪的锚点。
- 状态卡是**快照不是历史**。旧值除了「上章为」这一处，不保留。历史归时间线管。
- 只记录仍然有效的事实。角色死了、物品失去了，就从表里移除。

### 3.2 `state/hooks.md` —— 伏笔池

回答的问题：**"哪些坑还没填？"**

```markdown
# 伏笔池 · 截至第 NNN 章

| ID | 伏笔内容 | 埋设章 | 最近推进章 | 预计回收章 | 状态 | 债务 |
|---|---|---|---|---|---|---|
| H001 | <一句话> | 003 | 012 | 030 | 推进中 | 18 |
```

- `ID` 用 `H` + 三位序号，一旦分配永不复用。
- `状态` ∈ `已埋设` / `推进中` / `已回收` / `已废弃`。
- `已废弃` 需在伏笔内容里注明废弃原因。
- **回收或废弃后，把该行用 `AppendFile` 迁到 `state/hooks_closed.md`，并从 `hooks.md` 移除。** 审稿核对回收是否成立时读归档文件。

活跃表必须保持精简。如果把已回收的伏笔一直留在 `hooks.md` 里，到一百章时这张表会有上百行，而 `hooks.md` 是每章都要整份覆盖的，迟早会撞上输出上限被静默截断。归档表只追加，不受这个限制。

**债务算法**：

```
债务 = 当前章号 − 最近推进章号
```

`已回收` 与 `已废弃` 的伏笔债务记为 `—`。阈值：

| 债务 | 处置 |
|---|---|
| ≤ 20 | 正常 |
| > 20 | 审稿在评审中标注"伏笔停滞" |
| > 40 | 总编向用户提醒，建议安排推进或废弃 |

三类伏笔的合理配比：近期（5 章内回收）、中期（20 章内）、长线（全书）。同时存在超过 3 条长线伏笔通常意味着规划过载。

### 3.3 `state/timeline.md` —— 时间线

回答的问题：**"什么时候发生了什么？"** 这是累积型台账，**必须用 `AppendFile` 只追加新行**，绝不用 `EditFile` 重打整张表。**`content` 以换行开头**，理由见第一节的红框。

```markdown
# 时间线

| 故事内时间 | 事件 | 涉及角色 | 出处章 |
|---|---|---|---|
```

- `故事内时间` 用故事自身的纪年方式，与状态卡的「故事内时间」保持同一体系。
- 只记**有后续影响**的事件。日常过场不入表。
- 因为是追加写入，物理顺序就是章号顺序。倒叙、插叙导致故事内时间与章号不一致时，**不要为了排序去重排表**（那需要整份覆盖），在 `故事内时间` 列写清楚即可，读的人自己会排。

### 3.4 `state/cognition.md` —— 角色认知

回答的问题：**"谁知道什么？"** 这本账专治一类高频崩坏：**角色知道了不该知道的信息**。网文里信息差是剧情引擎，必须显式追踪。

```markdown
# 角色认知 · 截至第 NNN 章

## <角色名>
- knows: <该角色已知的关键信息清单>
- does_not_know: <该角色尚不知情的关键信息清单>
```

- 只登记**会影响行为决策**的信息，不是全部见闻。
- `does_not_know` 比 `knows` 更重要——它是防崩坏的护栏。写作时若某角色的行动依赖了 `does_not_know` 里的信息，就是崩坏。
- 只维护有信息差价值的角色（通常是主角 + 2-4 个关键角色），不是全部登场人物。
- **只要两个字段。** 不要再登记「读者已知但角色不知」——读者按定义知道正文里写过的全部事实，所以那一项完全可以由 `does_not_know` 推出（角色不知道的，就是悬念资产）。每章多维护一份可推导的清单是纯粹的 token 成本，也是台账膨胀的又一个来源。

### 3.5 `state/progress.md` —— 内容事实

唯一写入者：记账 Ledger。

```markdown
# 进度

- 已完成章数: N
- 最新完成章: NNN
- 累计字数（估算）: 约 NNNNN
- 当前弧: arcNN（起始章 NNN，预计结束章 NNN）
```

「累计字数」只能是估算，必须带「约」字。原因：LLM 数不准字数，而 `FileInfo` 只返回**字节数**（UTF-8 中文 3 字节/字，还含 Markdown 标记）。做法是把各章 `FileInfo` 的 `size` 相加再除以 3，取整到百位。**不要假装这是精确值**——它的唯一用途是让用户对进度有个量级感，不参与任何判定。

### 3.6 `state/run.md` —— 编排运行态

唯一写入者：总编 Muse。总编在**每次发起委派之前**更新 `在途工序`，这是崩溃恢复的唯一依据。

```markdown
# 运行态

- 在途工序: <无 | 执笔 ch012 | 审稿 ch012 | 修订 ch012 | 记账 ch012>
- 本章修订轮次: 0
- 待用户验收: <无 | ch012>
- 最后更新: YYYY-MM-DD HH:mm
```

## 四、工序产物模板

### 4.1 `plans/chNNN.plan.md` —— 节拍表

由执笔在写正文**之前**落盘。它是审稿核对"履约"的依据，顺序不可颠倒。

```markdown
# 第 NNN 章 节拍表

- 章节类型: <推进 | 爆发 | 铺垫 | 转折 | 日常过渡>
- 目标字数: 3000
- 本章目标: <一句话，本章要完成什么>
- 核心冲突: <一句话>
- 情绪弧线: <起点情绪 → 终点情绪>

## 场景推进项
1. <场景一要发生的事>
2. <场景二要发生的事>

## 爽点设计
- 位置: <前半 | 后半 | 章末>
- 类型: <打脸 | 反转 | 实力揭示 | 情感回报 | 信息差揭穿>

## 章末钩子
- 类型: <悬念 | 危机 | 信息揭示 | 情感悬置 | 反转预告>
- 具体内容: <一句话>

## 必须推进的伏笔
- H00X: <如何推进>

## 必须保留的一致性约束
- <从状态卡 / 角色认知中提取的硬约束>
```

「必须保留的一致性约束」是自我保护：把当前状态卡与角色认知里**本章容易踩**的条目摘出来，写作时对照。例如"主角尚不知道师父已死"。

爽点位置用「前半 / 后半 / 章末」三档粗粒度，**不要写"约第 12 段"或"全章 70% 处"**。三千字的章节里精确百分比无法核对，写了等于给审稿一个只能走过场的条目。粗粒度反而是可验证的：审稿能明确判断爽点落在前半还是后半。工艺上的目标位置（60–80%）由 `webnovel-craft` 给出，属于写作指导，不进节拍表。

### 4.2 `reviews/chNNN.verdict.md` —— 评审判决

由审稿落盘。格式细节与评分锚点见 `manuscript-review` 技能。

```markdown
# 第 NNN 章 评审判决

- 判定: <PASS | FAIL>
- 客观 AI 味分（WeWriteHumanness）: NN / 100
```

## 五、数据隔离边界

**记账只读终稿正文与上一版台账，不读节拍表、不读评审判决。**

这不是省 token，是防「立场后门」。如果记账看过评审意见，它会把"评审说这里写得好"当成客观事实写进状态卡；下一章的执笔读到这条，会以为那是已确立的设定。污染会顺着台账一路传递到全书。

同理，写章摘要时只依据正文里**真实发生的事**，不依据节拍表里**计划发生的事**。计划与成稿常有偏差，摘要必须记录后者。

---

## 六、冷启动 bootstrap

**为什么需要这一步。** `state/` 下的台账在每章末由记账刷新，但第 1 章的执笔在**写作前**就要读它们。而刷新用的 `EditFile` 遇到文件不存在会报错，记账的首棒也救不了场。如果不预先建出空台账，第 1 章的执笔所有 `ReadFile` 会全部 ENOENT，流水线在第一章就卡死。

所以**建基那一棒（架构师）必须顺带建出目录骨架与空台账**。

### 6.1 建目录

用 `CreateDirectory`（参数名是 `directoryPath`，不是 `filePath`），在 `file/novel/<book-id>/` 下建出：

```
state/  plans/  chapters/  reviews/  summaries/  arcs/  log/
```

### 6.2 用 `WriteFile` 落 6 份空台账

**空台账必须带完整表头**，这样执笔读到的是一份合法的空表，而不是空文件或报错。

### 6.3 摘要文件缺失不算失败

执笔要读「最近 3 章摘要」，但第 1–3 章时这些文件本来就不存在。

**读不到摘要文件时跳过，继续写作，不要判定任务失败。** 这是预期情况，不是错误。同理，第 1 章没有「上一章钩子」可以承接，开场自行建立情境即可。

## 七、落盘检查清单

每次写完台账，按顺序做完这三件事再收工：

1. 对每个写入的文件调 `FileInfo`，确认存在且 `size > 0`。
2. 对 `state/` 目录调 `ListDirectory`（参数名是 `directoryPath`，**不是 `filePath`**），确认恰好是 7 个文件（`status_card` / `hooks` / `hooks_closed` / `timeline` / `cognition` / `progress` / `run`）、**没有任何 `xxx(1).md`**。出现带序号文件说明该用 `EditFile` 的地方用了 `WriteFile`。
3. 在 `[[TaskComplete]]` 回执里列出所有验证通过的绝对路径。

若 `FileInfo` 异常，先重试一次、必要时改用 `ReadFile` 复核同一路径，不要因单次工具抖动就判定任务失败。
