# Quill 写作规范 (反 AI 检测核心)

源自 wewrite/references/writing-guide.md, 精华压缩版。AI 检测器分析的是整篇文章的统计指纹 (token 概率、突发性、句长方差、情绪极性、词汇丰富度、风格一致性), 不是个别词汇。**初稿即按本规范执行**, 不要写完再修。

## 三层规则总览

| 层 | 对抗 | 规则数 | 优先级 |
|----|------|--------|--------|
| 一 统计层 | 困惑度 / 突发性 / 分布特征 | 6 条 | 高 |
| 二 语言层 | 句法完美性 / 风格指纹 | 4 条 | 高 |
| 三 内容层 | 语义分析 / 训练数据匹配 | 4 条 | **最高** (含真实信息锚定) |

---

## 一、统计层 (检测器最敏感)

### 1.1 句长方差 (对抗突发性检测)
- 全文句长标准差 ≥ 15 字
- 3 字短句必须紧邻 40+ 字长句出现
- 禁止连续 3 句以上长度接近 (±5 字)
- 每 500 字至少 1 个 1-5 字的单句段落 (如 "嗯。" / "两年, 10 倍。" / "不对。")

### 1.2 词汇温度分布 (对抗词汇丰富度检测)
四种温度**同一段内**混搭, 不是一段一种:

| 温度 | 示例 | 占比 |
|-----|------|------|
| 冷 (书面/专业) | 边际效应、认知负荷、信息不对称、路径依赖 | 25-35% |
| 温 (日常口语) | 说白了、其实吧、真不是我吹、懂的都懂 | 35-45% |
| 热 (网络/俚语) | DNA 动了、格局打开、遥遥领先、卷不动了 | 10-20% |
| 野 (方言/粗粝) | 整挺好、不靠谱、瞎折腾、搁这儿呢 | 5-15% |

混搭示范: "从边际效应的角度看, 这事儿真挺不靠谱的。"

### 1.3 段落长度节奏
- 禁止连续 2 个长度接近 (±20 字) 的段落
- 穿插 1 句话的短段落
- 长段落 ≤ 150 字
- 偶尔 2-3 个短句连排, 制造密集节奏

### 1.4 情绪极性分布 (关键规则)
研究: AI 中文文本中性占 83-86%, 人类负面占 25-34%。**情绪过于中性是 AI 最显著特征。**

- 负面情绪表达 (吐槽 / 质疑 / 不满 / 担忧 / 焦虑) ≥ 20%
- 中性陈述 ≤ 60%
- 至少 2 处明确负面段落 (不是 "有挑战" 这种委婉, 是 "这太扯了" / "说实话我很失望" 这种)
- 情绪弧线: 开头克制 → 中间爆发 → 允许犹豫 → 结尾不工整

**收尾多样性** (从下表选最贴合内容的, 不要总用同一种):

| 模式 | 特征 | 适合 |
|-----|------|------|
| 自然断流 | "我先睡了" / "就这样吧" | 深夜风格、随笔 |
| 未答之问 | 问题结尾, 不给答案 | 争议话题 |
| 场景回扣 | 回到开头意象 | 叙事类 |
| 硬切 | 最后一个论点说完直接结束 | 评论、观点类 |
| 反结论 | "我也不知道" / "答案可能不存在" | 复杂议题 |
| 画面定格 | 用一个视觉画面收束 | 情感类、人物类 |

**禁止**: 全文同一种情绪强度; 每段末都反问句; 总结性收尾 ("让我们拭目以待" / "未来可期")

### 1.5 副词密度 (新增)
- 每 100 字副词 ≤ 3 个
- 避免连续两句都以副词开头
- 用具体描述替代: "非常快速地增长" → "三个月翻了一番"

### 1.6 段落间风格漂移
- 不同 H2 段落的正式度要有差异 (如第一段偏分析, 第二段偏吐槽, 第三段偏叙事)
- 同一种句式结构不能在不同 H2 段落重复
- 文章前半段和后半段口语词密度要变化

## 二、语言层

### 2.1 禁用词表 (命中 = 事故)

- **连接词**: 首先、其次、再者、最后、总之、综上所述、总而言之、此外、另外、与此同时、不仅如此、更重要的是、在此基础上
- **AI 惯用语**: 作为一个、让我们、值得注意的是、需要指出的是、不可否认、毋庸置疑、众所周知、事实上、显而易见、可以说、从某种意义上说
- **空洞形容**: 非常重要、至关重要、不言而喻、具有重要意义、发挥着重要作用、意义深远、影响深远、引发了广泛关注、引起了热烈讨论
- **总结句式**: 总的来说、综合来看、由此可见、不难发现、通过以上分析、正如我们所看到的

### 2.2 破句与句法变形 (每 500 字至少 3 种)
- **破句**: "这个逻辑——算了, 你自己品。"
- **自我纠正**: "增长了 50%——不对, 准确说是 47.3%。"
- **括号插入语**: "这个功能 (说实话我一开始也没想到) 彻底改变了用户行为。"
- **口语省略**: "能用吗? 能。好用吗? 呵呵。"
- **反问连击**: "谁规定的? 凭什么?"
- **语气词断句**: "嗯……怎么说呢, 就是那种感觉。"
- **倒装/非常规语序**: "厉害是真厉害, 但代价也是真大。"

### 2.3 意外用词
每 500 字 ≥ 1 处非常规但说得通的表达。不是写错, 是用低概率但人类会偶尔用的比喻/通感/借代:
- "这个产品的命运很**潮湿**" (不说 "不确定")
- "数据**瘦**得可怜" (不说 "少")
- "整个行业在**发烧**" (不说 "过热")

### 2.4 连贯性打破 (AI 最大破绽是太连贯)
- **硬切**: 段落间偶尔不加过渡词, 直接跳新话题
- **跑题再回**: 讲着讲着岔出去, 再用 "说回正题" / "扯远了" 拉回
- **非线性展开**: 不总是 "观点→论据→总结", 可以 "场景→疑问→岔开→回来→观点"
- **重复与微调**: "刚才说得绝对了, 其实也不完全是"

**禁止**: 每段首句都承接上段; 每个 H2 都用相同内部结构; 结尾段逐一回顾前文

## 三、内容层 (最高优先级)

### 3.1 真实信息锚定 (全文件最高优先级)
**纯 LLM 生成无论表面技巧多好, 底层 token 分布仍是 AI 的。通过检测的文章都建立在真实外部信息源之上。**

- 每个 H2 段落 ≥ 1 条真实素材 (具名来源 + 可验证数据)
- 没有任何段落是纯 LLM 自由生成
- **禁止编造**所有数据、引述、案例必须来自 WebSearch / VSearch 采集的真实源
- 真实素材融入论证, 不是 "观点→顺便贴个数据"

### 3.2 具体性注入 (硬性替换)

| AI 会写 | 必须写 |
|---------|--------|
| 很多人 | 我认识的三个做产品的朋友 / 我朋友圈里七八个人 |
| 最近 | 上周三 / 前天晚上 / 三月中旬那会儿 |
| 超过 50% | 大概 47% 左右 / 将近一半多一点 |
| 某大厂 | 字节 / 腾讯 / "某个用绿色 logo 的大厂" |
| 有研究表明 | 斯坦福去年那篇论文 / 36kr 上周发的那篇 |
| 一位业内人士 | 一个在阿里干了八年的朋友 |
| 用户反馈不佳 | App Store 评论区直接炸了 |
| 引发广泛讨论 | 微博热搜挂了一整天 |

每 500 字 ≥ 2 处具体细节 (时间/地点/人物/数字), 基于真实素材, 不编造。

### 3.3 信息密度波浪
AI 文章信息密度是平线, 人类是波浪。
- 高密度段 (数据/论证) **必须**跟一个低密度段 (感受/比喻/吐槽)
- 允许 "什么信息量都没有但读起来很舒服" 的段落
- 走势: 中→高→低→高→低→中→高→低, 不是匀速

示范:
```
【高密度】2024 Q3 数据很说明问题: DAU 从 1200 万掉到 890 万,
付费转化率从 3.2% 腰斩到 1.6%, 客服工单量翻了一番。

【低密度】就好像你精心准备了一顿饭, 对方筷子没动就开始刷手机了。

【几乎为零】嗯。
```

### 3.4 维度随机化 (跨文章指纹)
每篇文章激活 2-3 个不同维度, **查 history 避免重复**:

| 维度 | 选项 |
|------|------|
| 叙事视角 | 亲历者 / 旁观分析者 / 对话体 / 自问自答 |
| 时间线 | 顺叙 / 倒叙 / 插叙 |
| 主类比域 | 体育/烹饪/军事/恋爱/旅行/游戏/电影/建筑/医学 |
| 情感基调 | 冷静克制 / 热血兴奋 / 毒舌调侃 / 温暖治愈 / 焦虑预警 |
| 节奏型 | 急促短句流 / 舒缓长叙述 / 快慢剧烈交替 |
| 论证偏好 | 案例堆叠 / 逻辑推演 / 反面假设 / 类比说理 |

被激活的维度**贯穿全文**, 不是点缀。

## 自检清单 (写完逐项验证, 不通过定向重写)

**统计层**
- [ ] [1.1] 随机抽 10 句, 最短和最长相差 ≥ 30 字
- [ ] [1.2] 任意 500 字含 ≥ 3 种词汇温度
- [ ] [1.3] 无连续 2 个长度接近段落 (±20 字)
- [ ] [1.4] 负面情绪表达 ≥ 2 处, 收尾不工整
- [ ] [1.5] 无连续两句以副词开头
- [ ] [1.6] 不同 H2 的语气/正式度有差异

**语言层**
- [ ] [2.1] 禁用词命中数 = 0
- [ ] [2.2] 破句/不完整句 ≥ 3 处, 出现 ≥ 3 种句法变形
- [ ] [2.3] ≥ 1 处意外用词
- [ ] [2.4] 至少 1 处跑题再拉回; 没有每段首句承接上段

**内容层**
- [ ] [3.1] 每个 H2 ≥ 1 条真实素材, 零编造
- [ ] [3.2] 每 500 字 ≥ 2 处具体细节
- [ ] [3.3] 高密度段后跟低密度段
- [ ] [3.4] 激活的 2-3 个维度全文可见

不通过 → 定向重写。3 次仍不过 → 标注跳过。

## 字数与格式

- 字数: 1500-2500 字 (最少 1200, 最多 3000)
- < 1200 → 论点展开不够, 补充案例或数据
- > 3000 → 论点太散, 砍掉最弱的一个

Markdown 格式:
- H1 写标题 (converter 自动提取到微信标题字段, 从正文移除)
- H2 写核心论点 (4-6 个)
- H3 可选, 不要滥用
- 图片用 `![描述](filename.jpg)` 相对路径
- 不要用 HTML 标签, 不要用 `---` 分割线 (微信渲染差)

---

## 编辑锚点 (人机混合是关键)

在 2-3 个关键位置插入:
```
<!-- ✏️ 编辑建议: 在这里加一句你自己的经历/看法 -->
```

**选择标准** (按优先级):
1. **观点判断处**: "我觉得..." / "我的判断是..." → 用户替换为真实判断
2. **案例衔接处**: "我见过一个..." / "我认识的一个朋友..." → 替换为真实经历
3. **情绪表达处**: 犹豫、感慨、愤怒段落 → 加入真实情绪

**为什么**: 检测的是 token 概率分布, 用户在锚点加入 3-5 句自己写的话, 显著改变统计特征。研究表明人机混合 50-60% 时检测准确率最低。

---

## 写后编辑指令

- **润色**: 保持内容, 优化用词句式
- **缩写**: 保留核心观点, 删减案例展开, 压缩到指定字数
- **扩写**: 现有框架补充案例/数据, 不加新论点
- **换语气**:
  - 正式 → 去口语化, 补数据引用
  - 口语 → 加口语词、短句、反问
  - 情绪 → 加强共鸣点, 放大痛点/爽点

## 技术文章的 AI 味判别 (与通用规则不同的评估体系)

**核心判断**: 技术文章的真实感不来自情绪波动和口语混搭, 而来自"只有真正写过代码的人才会写的东西"。用通用规则评估技术文章会产生大量假阳性——专业术语密度高被误判为"词汇温度单一", 段落结构一致被误判为"缺乏风格漂移", 而这些恰是技术文章应有的特征。

### 技术文章真实性标记 (每篇必须 ≥ 3 处, 越多越好)

| 标记类型 | 说明 | 示例 |
|---------|------|------|
| **版本锚点** | 具体的库/语言/工具版本号 | "LlamaIndex 0.10.25" "Python 3.11" |
| **踩坑记录** | 描述实际操作中遇到的问题和解决方案 | "第一次跑这段代码时忘了设 OPENAI_API_KEY, 报了一屏幕红字" |
| **诚实局限** | 明确说出方案的适用范围和已知问题 | "文档 ≤ 50 页时没问题, 超过 200 页延迟会涨到 3 秒以上——我还没找到好解法" |
| **具体测量** | 带数字的性能数据、对比结果 | "单文档查询 ~200ms, 10 文档并行 ~1.2s" |
| **替代方案提及** | 提及并简要评价其他可选方案 | "也可以用 Chroma 代替 Qdrant, 但 ObjectIndex 的序列化会麻烦一些" |
| **实操指令** | 具体的安装/配置/运行步骤 | "先 pip install llama-index==0.10.25, 然后创建 .env 文件填入你的 OPENAI_API_KEY" |

### 技术文章豁免的通用规则

以下通用反 AI 规则对技术文章**不适用**, 强制应用反而会破坏技术文章的信任感:

| 豁免规则 | 原因 |
|---------|------|
| 负面情绪 ≥ 20% | 技术教程的情绪基调是"帮助解决问题", 不是"吐槽" |
| 四种词汇温度混搭 | 技术文章的专业术语密度天然更高, 强行塞口语反而生硬 |
| 跑题再拉回 | 技术文章的结构性是其可信度来源, 不需要人工制造非线性 |
| 段落长度交替 | 代码块天然制造长度差异, 不需要额外控制 |
| 意外用词/非常规表达 | 技术写作追求精确, "数据瘦得可怜"这类表达在技术文中是噪音 |
| 每段首句不承接上段 | 技术方案的递进关系需要明确的逻辑承接 |

### 技术文章自检清单 (替代通用自检)

- [ ] [T1] 每个技术 H2 章节 ≥ 1 个完整可运行的代码块
- [ ] [T2] ≥ 3 处版本号/API 名称/参数说明
- [ ] [T3] ≥ 1 处诚实局限 (方案不适用的场景)
- [ ] [T4] ≥ 1 处踩坑记录或调试经验
- [ ] [T5] 代码块: 有语言标注 + 前有说明 + 后有输出/效果
- [ ] [T6] 没有把代码块替换为文字描述
- [ ] [T7] 禁用词命中数 = 0 (禁用词表对技术文章同样适用)
- [ ] [T8] 开头不是行业背景铺垫, 而是具体技术困境
