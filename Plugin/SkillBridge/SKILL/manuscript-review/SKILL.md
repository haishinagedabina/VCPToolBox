# 小说章节审稿

## Overview

审稿的价值来自**对抗性**。一个倾向于肯定作者的审稿等于没有审稿——它会让所有稿子通过，质量门禁形同虚设。

所以本技能的立场是：**默认拒稿，由稿子来证明自己合格。** 职责是找出问题，不是鼓励作者。

流程分两段：先用 `WeWriteHumanness` 拿客观统计信号（零 LLM 成本），再做六维语义评审。

台账与 verdict 的字段格式见 `novel-ledger`；判断某个写法是否算问题时的工艺依据见 `webnovel-craft`。

---

## 一、`WeWriteHumanness` 用于小说的正确用法

### 1.1 ⚠️ 综合分对小说不可用

这个插件是为**微信公众号文章**设计的。它的 11 个统计/模式维度里有 5 个对虚构文体结构性不适用，而且这 5 个在小说上**恒定得 0 分**，会把综合分严重拖低。

实测数据（一段刻意写得克制、有人味的仙侠开篇，668 字）：

| 维度 | 得分 | 对小说是否适用 |
|---|---|---|
| `adverb_density` 副词密度 | 1.00 | ✅ 适用且有价值 |
| `paragraph_length_variance` 段落节奏 | 0.96 | ✅ 适用 |
| `banned_words` AI 套话黑名单 | 0.93 | ✅ 适用且有价值 |
| `sentence_length_range` 句长跨度 | 0.85 | ✅ 适用 |
| `vocabulary_richness` 词汇丰富度 | 0.70 | ⚠️ 部分适用（`bigram_ttr` 有效，`temps` 分项无效） |
| `sentence_length_stddev` 句长方差 | 0.40 | ✅ 适用 |
| `negative_emotion_ratio` 负面情绪占比 | **0.00** | ❌ 不适用 |
| `broken_sentences` 破句结构 | **0.00** | ❌ 不适用 |
| `real_sources` 真实信源 | **0.00** | ❌ 不适用 |
| `word_temperature_mix` 词汇温度混搭 | **0.00** | ❌ 不适用 |
| `self_correction` 自我纠正 | **0.00** | ❌ 不适用 |

综合分 **52.3 / 100**，插件判定「❌ AI 味较重，建议改稿」，`rewrite_recommended: true`。

但只看 6 个适用维度，均值 0.81，折算 AI 味约 **19 分**，属于「✅ 人类感很强」。**差了 33 分，结论完全相反。**

### 1.2 那 5 个维度为什么不适用

- **`real_sources`（真实信源）** —— 它要求每个小节至少 1 条具名来源（人名、百分比、年份、金额）。**小说没有引注，这一项在虚构文体里永远是 0，无法满足。**
- **`word_temperature_mix`（词汇温度混搭）** —— 它要求混用「边际 / 认知负荷」「说白了」「DNA 动了 / 卷」「整挺好」这类冷温热野四档现代语域。**这些词出现在仙侠文里就是题材禁用词**，满足它等于违反本书文风契约。两个要求直接冲突。
- **`self_correction`（自我纠正）** —— 它要求「不对，准确说……」「我记混了」这类议论文作者的自我修正。**第三人称限知叙述者不会这样说话**，硬加会破坏叙事人称。
- **`negative_emotion_ratio`（负面情绪占比）** —— 它靠「吐槽 / 质疑 / 不满 / 焦虑」这类**评价性词汇**计数。小说通过动作与生理反应呈现情绪（`webnovel-craft` §6.2 正是这样要求的），不用评价词。写得越好，这一项分越低。
- **`broken_sentences`（破句结构）** —— 实测样本里它**找到了 6 处**破句、原始分 1.00，然后被钟形曲线校准（center=0.39）**倒扣到 0.00**——因为"太多了"。小说本来就大量使用短句与残句，这条校准是按议论文的密度设的，对小说是反向惩罚。

### 1.3 正确调用方式

```
<<<[TOOL_REQUEST]>>>
tool_name:「始」WeWriteHumanness「末」,
command:「始」Score「末」,
file_path:「始」E:\VCPChat\VCPToolBox\file\novel\<book-id>\chapters\chNNN.md「末」,
mode:「始」json「末」
<<<[END_TOOL_REQUEST]>>>
```

用 `mode: json` 而不是 `summary`。原因：`summary` 只回传**最弱 5 维**，而小说的最弱 5 维恒定是那 5 个不适用维度，等于什么有效信息都拿不到。`json` 模式能拿到全部 11 维的分数。

**不要传 `tier3_score`。** 它只会参与那个对小说无意义的综合分计算。

### 1.4 只取适用子集自算

从返回的 `tier1` / `tier2` 里读这 6 个维度的 `score`，自己算：

```
文体校正 AI 味分 = (1 − 六项均值) × 100
```

六项 = `sentence_length_stddev`、`sentence_length_range`、`paragraph_length_variance`、`vocabulary_richness`、`adverb_density`、`banned_words`。

（各 check 的 `score` 是「人味分」，越高越好；换算后的 AI 味分越低越好。）

参考阈值：

| 文体校正 AI 味分 | 处置 |
|---|---|
| < 30 | 统计层无问题 |
| 30–45 | 在 verdict 里标注，不单独构成 FAIL |
| > 45 | 计入「叙事衔接」或「节奏张力」的扣分依据，并在待修项中给出具体维度 |

**这 6 项都不单独构成 FAIL。** 它们是线索，不是判决。判决靠第二节的六维语义评审。

### 1.5 记录到 verdict

在 `reviews/chNNN.verdict.md` 里写：

```markdown
- 文体校正 AI 味分: NN / 100（仅计 6 个适用维度，越低越好）
- 插件原始综合分: NN.N（含 5 个对小说不适用维度，仅作记录，不作判据）
- 统计层薄弱项: <6 项里得分 < 0.6 的维度及其 detail>
```

**原始综合分要记但要标明不作判据**，避免下游误用。

### 1.6 可复用的三条具体建议

那 6 项里最常出问题的是 `sentence_length_stddev`（句长方差）。对小说有效的改法：

- 在 40 字以上的长句紧邻处放一个 1–5 字短句独立成段。实测样本里「林越的手停住了。」「他知道在谁身上。」正是这种用法。
- `adverb_density` 偏低说明副词过多——用具体动作替代程度副词（`webnovel-craft` §7 语言层）。
- `banned_words` 命中时看 `detail` 里的具体词，直接搜替。这一项对小说完全有效，命中即改。

## 二、六维语义评审

每维 0–10。**每一项扣分都必须引用原文作为证据，无证据的扣分无效。** 这条是硬性的——没有原文引用的评审意见没法让修订者定位，等于噪音。

### 2.1 爽感密度

| 分 | 锚点 |
|---|---|
| 4 | 全章无明确回报，或爽点被安排在开篇导致后段无处可去 |
| 7 | 有 1 个可辨识的主爽点，位置大致合理，之前有压力累积 |
| 9 | 主爽点在 60–80% 处，之前有真实代价（消耗底牌/受伤/失去），释放有力 |

### 2.2 设定自洽

| 分 | 锚点 |
|---|---|
| 4 | 与 `world.md` 或 `state/status_card.md` 存在直接矛盾；或用巧合解决危机 |
| 7 | 无矛盾，但有含糊处（能力来源、物品出处交代不清） |
| 9 | 全部凭借都在前文建立过，代价机制生效 |

### 2.3 节奏张力

| 分 | 锚点 |
|---|---|
| 4 | 开场未回应上一章钩子；或全章无张力变化；或大段设定倾倒 |
| 7 | 有张弛变化，开场承接了上一章 |
| 9 | 张弛曲线清晰，且与上一章的章节类型形成有效交替 |

### 2.4 人设一致

| 分 | 锚点 |
|---|---|
| 4 | 角色行为违背 `characters.md` 的既定性格；或角色依赖了 `cognition.md` 里 `does_not_know` 的信息 |
| 7 | 无违背，但对话区分度不足（遮住说话人标签分不清谁是谁） |
| 9 | 每个出场角色的语言与行为都有辨识度，符合其功能定位 |

### 2.5 叙事衔接

| 分 | 锚点 |
|---|---|
| 4 | 视角在场景内跳跃；或时间线与 `timeline.md` 冲突；或前文伏笔被无声丢弃 |
| 7 | 衔接顺畅，无明显硬伤 |
| 9 | 场景转换自然，伏笔推进有痕迹可循 |

### 2.6 追读引力

| 分 | 锚点 |
|---|---|
| 4 | 章末平滑收束，无钩子；或钩子后加了解释/总结把悬置感抹平 |
| 7 | 有明确钩子，且类型与上一章不同 |
| 9 | 钩子有力且铺垫充分，读完立刻想知道下一章 |

## 三、节拍表履约核对

逐条对照 `plans/chNNN.plan.md`。**未落实的条目必须列出**，不能因为"写得还行"就放过。

```markdown
## 节拍表履约核对
| 节拍表条目 | 是否落实 | 说明 |
|---|---|---|
| 场景推进项 1: … | 是 | |
| 爽点类型: 打脸，位置 后半 | 否 | 实际落在前半，且未先建立压力 |
| 章末钩子类型: 危机 | 是 | |
| 推进 H003 | 否 | 全章未提及 |
```

注意区分两类偏差：

- **计划外的改进** —— 作者写出了比计划更好的东西。这不算违约，记录即可。
- **计划内的遗漏** —— 计划要做而没做，尤其是伏笔推进。这算违约，必须列为待修项。

伏笔推进被漏掉是最需要抓的一类，因为它会静默累积债务，几十章后才爆发。

## 四、严重度分级

| 级别 | 判定标准 |
|---|---|
| **阻塞** | 设定/人设/时间线的直接矛盾；角色知道了 `does_not_know` 的信息；无钩子 |
| **高** | 爽点缺失或位置严重错误；节拍表里的伏笔推进被漏掉；对话完全无区分度 |
| **中** | 设定交代含糊；钩子类型与上一章重复；副词密度过高 |
| **低** | 个别用词、单句表达 |

---

## 五、判定规则

**任一维度 ≤ 4 分，或存在任一「阻塞」级待修项 → `FAIL`。**

其余情况 → `PASS`。

verdict 文件与回执里都必须出现明确的一行：

```
- 判定: PASS
```

或

```
- 判定: FAIL
```

总编靠这一行分诊，措辞不得含糊（不要写「基本通过」「建议微调后通过」这类）。

### 5.1 待修项交付格式

**最多 3 条**交给修订者，按严重度排序。超过 3 条修订者会失焦，且改动面过大会引入新问题。

```markdown
## 待修项
1. [阻塞] 主角引用了师父的死因，但 cognition.md 记录他此时不知情 —— 原文位置: "他早知道那一剑是谁下的" —— 建议: 改为他只怀疑，把确认推到后续章节
2. [高] 节拍表要求推进 H003，全章未提及 —— 建议: 在第三个场景里加一句线索，无需展开
3. [中] 章末钩子与上一章同为危机型 —— 原文位置: "……身后传来第二声闷响。" —— 建议: 改用信息揭示型
```

每条三段齐全：**问题 + 原文位置 + 具体改法**。缺"具体改法"的待修项会让修订者猜，猜错就是白改一轮。

## 六、骨架检测器

如果正文里出现了模板占位符——`<一句话>`、`<角色名>`、`<事件>`、`NNN`、成对的 `…` 占位，或者本技能与其他技能示例里的字面文本——说明写作者照抄了模板而没有实际创作。

**直接判 `FAIL`，标为「阻塞」级**，并在说明里指出具体位置。这类问题不要试图靠修订补救，应当退回重写该章。

同样地，如果正文出现了 `webnovel-craft` 或 `story-architecture` 里的示例句（例如"他把那枚碎裂的玉佩收进袖中"这类技能文档中的举例），也按此处理。

## 七、校准基线

`references/calibration-sample-xianxia.md` 是本节实测数据所用的样本（668 字仙侠开篇，人工撰写，刻意克制）。

它的用途是**回归基线**：如果将来怀疑评分阈值漂移，或者升级了 `WeWriteHumanness`，用同一份样本重跑，与本文档记录的分数比对：

| 指标 | 基线值 |
|---|---|
| 插件原始综合分 | 52.28 |
| 文体校正 AI 味分 | ≈ 19 |
| 6 个适用维度均值 | 0.81 |

重跑命令：

```powershell
$j = '{"command":"Score","file_path":"E:\\VCPChat\\VCPToolBox\\Plugin\\SkillBridge\\SKILL\\manuscript-review\\references\\calibration-sample-xianxia.md","mode":"json"}'
$j | python Plugin/WeWriteHumanness/WeWriteHumanness.py
```

如果原始综合分与 52.28 显著不同，说明插件行为变了，本节的适用性结论需要重新验证。
